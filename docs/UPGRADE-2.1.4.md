# Catching up with opencode 2.1.4

Status: batches 1 to 7 done, batch 8 (experimental) not started (analysis 2026-10-25). The [progress table](#progress)
lists what each batch ported and how it was checked.

Before this catch-up ocd replicated upstream commit `4617210` (version 2.0.26, the head of upstream's `v2`
branch). That branch has not moved since; v2 development continued on `dev` and was released as v2.1.0 to v2.1.4 (Oct 20 to 23). From
`4617210` to `v2.1.4` there are 536 commits. About half of them touch packages ocd doesn't replicate (web
console, website, desktop app, stats).

How this was made: six read-only reviews of `git diff 4617210 v2.1.4`, one per area, each checked against
ocd's current code. Sizes are developer-day estimates for porting faithfully, useful for comparing items
rather than as a schedule. The detailed findings, one table per area, are in the
[appendix](#appendix-findings-per-area).

## Do first: data shared with upstream

ocd and opencode share the same files: `opencode.db`, `auth.json` and `service-<channel>.json`.

1. **The v2.1 data rename.** Upstream renamed provider data in stored session events and messages:
   - `state`/`providerState`/`resultState` become `native`;
   - a compaction row drops `recent`/`providerContext` and refers to kept messages with `metadata.keepID`;
   - key credentials move `configuration` into `metadata`.

   Upstream upgrades old rows when it reads them. ocd's types require the old fields (`recent: String` in
   `oc-schema/src/message.rs`). So a session written or compacted by upstream 2.1 can fail to load in ocd,
   and the new web UI reads only the new names. Port the rename together with upgrade-on-read before
   anything else.
2. **The new migration** (`20261010180456_project_time_archived`). ocd tolerates a database where it has
   already been applied (unknown migration ids are skipped and the extra column is harmless). ocd should still
   add it, because project archiving needs it.
3. **The service file.** ocd registers version 2.0.26 and drops the new `remoteAccepted` field when it rewrites
   `service-<channel>.json`. While upstream 2.1 runs on the same machine, the two can keep replacing each

## Proposed order

1. **Data compatibility** (about 8 to 10 days): the v2.1 rename with upgrade-on-read, credential `metadata`,
   the migration, and the service file fields.
2. **Provider and catalog fixes** (about 6 days): the quick provider wins, the snapshot, the background
   refresh, tolerant stream decoding, Gemini continuation, `encoding`/`cacheFormat`/`streamUsage`, and the
   config provider overlay.
3. **Session and tools** (about 10 days): the compaction rewrite (rows 2 to 5 of the core session table,
   ported together), continuing after output limits, titles, the edit tool, MCP media results, and the shared
   retry policy.
4. **Platform and config** (about 10 days): `instructions`, substitution, managed system config, top-level
   `policies`, bounded skill discovery, sandbox tolerance, the MCP fixes, and the plugin API additions with a
   rebuilt plugin host.
5. **HTTP API** (about 6 days): session archiving, editing saved permissions, project archiving, the
   free-limit error, the `type=idle` filter, and regenerating `generated.rs` from the 2.1.4 OpenAPI document.
6. **TUI** (about 15 days): the dialog layout refresh, the diff side panel (opened by default) and its compact
   layout, the free-limit notice, `/copy`, terminal status reporting, and the archiving UI.
7. **Release** (about 3 days): report 2.1.4, rebuild the web UI from `v2.1.4`, regenerate the golden CLI
   help, and rerun the parity suite against an upstream 2.1.4 binary.
8. **Experimental, optional:** new designs, `todowrite`, background compaction, client MCP, voice, and
   `location_idle_timeout`.

Risks / open questions
- **Rename collision (row 2).** It touches every assistant/compaction row and event ocd has stored, and the DB is shared with upstream. Ship the legacy upgrade-on-read together with the rename, or old sessions will lose their native replay data (reasoning signatures, response IDs).
- **Codegen gaps.** `gen.py` must special-case the new `x-websocket` op and the token op. The OpenAPI document drops the `name` regex check (row 4) and the import `messages` item schema (row 2), so ocd's openapi-driven validation will accept inputs that upstream rejects unless those checks are added by hand.
- **Location idle timeout (row 8).** This depends on a pre-existing ocd gap, the missing LocationActivity eviction. Decide whether to port the whole idle-unload behavior or only accept the config key.
- **Cursor byte-for-byte parity.** The parity suite may compare `cursor.previous/next` strings exactly. The `archived` key must serialize as a string after `parentID`, as in upstream.
- **Voice (row 7).** It needs live OpenAI/xAI/Google realtime endpoints and the OpenCode Console host plugin, and cannot be parity-tested offline. Consider deferring it.

- **OSC 7501 format (#7):** `createProgramStatus` calls OpenTUI 0.6.5's `renderer.setProgramStatus`. That source is not in the local checkouts (`node_modules` only has `@opentui/core` 0.5.17).
