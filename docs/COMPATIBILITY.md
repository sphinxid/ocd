# Compatibility with opencode

[← README](../README.md)

ocd targets opencode **2.4.1** (`anomalyco/opencode`, tag `v2.4.1`, commit `6f05140`). It was first ported from
branch `v2` at commit `4617210` (2.0.26). It then caught up with 2.1.4, 2.2.2, 2.2.5, 2.2.7, 2.3.0, 2.3.1, 2.3.2 and 2.4.1 in batches, listed with
what each one checked in [UPGRADE-2.1.4.md](UPGRADE-2.1.4.md), [UPGRADE-2.2.2.md](UPGRADE-2.2.2.md),
[UPGRADE-2.2.5.md](UPGRADE-2.2.5.md), [UPGRADE-2.2.7.md](UPGRADE-2.2.7.md), [UPGRADE-2.3.0.md](UPGRADE-2.3.0.md), [UPGRADE-2.3.1.md](UPGRADE-2.3.1.md), [UPGRADE-2.3.2.md](UPGRADE-2.3.2.md) and [UPGRADE-2.4.1.md](UPGRADE-2.4.1.md). Wherever it has to look like opencode,
ocd reports version 2.4.1.

## How it is compared

- **Side by side:** both binaries run the same 310 scenarios, and `scripts/parity.py` diffs their outputs. Results
  are in [PARITY.md](PARITY.md). The scenarios cover:
  - the agent loop, sessions, permissions and forms;
  - the read-only endpoints and 74 error cases;
  - the CLI and plugins;
  - GitHub Copilot, the OpenAI WebSocket transport and the experimental todo list;
  - the 2.2 changes: provider wire, `/goal`, background compaction and tools;
  - Mercurial repositories and the desktop browser attachment;
  - the 2.2.7 changes: `run`, MCP OAuth, Copilot Auto, tools, the API and config;
  - the 2.3.0 changes: freeform tools, subagent reports, the step lifecycle, Code Mode search and `fetch`,
    MCP OAuth refresh, pasted sign-ins and client certificates;
  - the 2.3.1 changes: the automation migrations and automations, `Buffer` and argument crossing in Code Mode,
    shell timeouts, read shapes, readable 500s, reasoning replay, ACP background shells and daemon shells across a restart;
  - the 2.3.1 Code Mode changes: `Buffer`, arguments crossing as copies, plugin renames and nested permission rows;
  - the editor integration (ACP) following subagents and background shells after a turn;
  - the 2.3.1 changes: the API (automation, video and blob routes) and config keys;
  - the 2.3.1 provider and server changes: reasoning replay, the ChatGPT token-sharing catalog, video models in the
    catalog, storage failures answering readable 500s, and the local agent CLI's context check;
  - local model discovery for LM Studio, Ollama and vLLM against mock servers;
  - the opt-in part rows, and the opt-in MCP features: connection pooling, MCP Events with the watch tool, and
    automation event triggers;
  - opt-in session warming: every keep-alive request of a warming cycle and what it stores;
  - the 2.3.2 changes, through the scenarios above: Responses requests leading with the system prompt as a developer
    message, and `webfetch`'s smaller output;
  - the 2.4.1 changes: tool repair, result field order, background results, shell permissions and job cancel
    (`session241`), the provider wire (`wire241`), MCP (`mcp241`), video generation (`video`) and the local agent
    CLI provider (`claude241`), plus automations on by default and the new built-in plugins through the scenarios
    above;
  - client-hosted MCP: a scripted client hosting tools over the WebSocket endpoint, the model calling them, stacked
    clients, tickets, refusals and close codes.
- **Model requests:** every request ocd sends to the model is compared too: system prompt, tool definitions,
  headers and prompt-cache markers.
- **Result:** 281 of the 309 scenarios run against 2.4.1 are identical (`fcm231_all_flags` is not run, because
  `experimental.all_flags` turns on 2.4.1's `machines`, whose iroh endpoint is not plain HTTP). The other 28 differ in
  ways that are expected or recorded as gaps ([PARITY.md](PARITY.md)):
  - the intended renames, and the upstream test build's database file name;
  - timing: an upstream retry race, a signal racing the debug build's first step, and the order of an
    `experimental.job.updated` against the step's `session.usage.updated` when a foreground shell command ends;
  - the order of tool-failure events for calls that fail instantly, which upstream gets from its runtime's scheduler;
  - the order of two directories with the same score in fuzzy file search;
  - the reference build serving its web UI, which the debug build compared has not embedded;
  - 2.4.1's desktop browser plugin changes, not ported yet (its skill text and tools);
  - opt-in features ported only partly: full Code Mode and the OpenCode Console's artifacts and watches.

- **Per-crate tests:** each crate has its own test suite, many replaying recorded upstream data.

## Same as upstream

| Area | Notes |
|---|---|
| Sessions and history | Create, fork, revert, export, import and search (title search folds case beyond ASCII from 2.3.1; generated titles are cut on whole characters). The same database file and schema (2.4.1's 64 migrations: the `automation` table, with live schedules that have no check or run limit copied into it, no `schedule` table, and 2.4.1's `machine` table, which ocd creates but does not use yet; ocd and upstream 2.4.1 open each other's databases, and ocd no longer checkpoints the WAL on open, like 2.4.1). From 2.3.0 every fork gets the `<fork-notice>` message in its inbox (`msg_fork_notice_<id>`, without resuming it; the built-in `opencode.fork-notice` plugin, listed in `plugin.list`), and an instruction update a committed revert left behind is hidden from the model once a fresh baseline covers it |
| Tool input repair | Malformed tool inputs are repaired against the tool's schema before validation, as upstream's `opencode.tool.input.repair` does: numbers and booleans sent as strings, extra keys on closed schemas, stringified JSON, empty placeholders, single values for arrays. For built-in, Code Mode, MCP and plugin tools; `-opencode.tool.input.repair` turns it off |
| Agent loop | Steps, tool calls, reasoning, retries, compaction (including background compaction: on by default since 2.3.1, off with `compaction.background: false`; a held summary also serves a model or instructions change and an overflow, and starts even past the threshold), titles, background jobs and subagents. 2.3.0's step lifecycle: a stream that fails after output started is retried into a fresh message without a "continue" prompt, and a failed or interrupted message is replayed cut at its last local call that ran; the durable `session.step.first-token` event and `time.firstToken` (the TUI's tokens/s count from the first token and the footer shows the time to it); a user's stop lets tools that listen for it settle their own calls within 5 s and interrupts the others |
| Subagents (2.3.0) | Subagents always run in the background: the `subagent` tool has no `background` input and returns the running handle at once. The parent gets a `<background-result kind="subagent">` report each time a child goes idle (after follow-ups, wakes from the child's own background work, and for children created and prompted directly over HTTP), listing background work still running and then tagged `state="running"`; a stopped child reports "Subagent cancelled". The job row is written when the job starts and updated in place as the report's outbox, in the same commit as the claim release; from 2.3.1 the outbox keeps the raw body and a snapshot of the work still outstanding, and the `running` state and still-running list come from that snapshot. After a restart, wakes wait until every suspended session counted its attempt, directly driven children resume, and only orphaned child claims are released |
| `/goal` | The command and its controls, the reviewer loop, the `opencode.goal` RPC and its event, and the TUI's footer status and dialog |

Subagent sessions are never warmed; a cache that outlives the window isn't; a ping waits for a running request or compaction and gives up once the cache it would keep has expired; a ping that writes more cache than it reads stops warming until the next real request; a failed ping is logged and the next one comes an interval later; deleting the session, closing its location or turning the plugin off stops it |
| Permissions and forms | Ask, once, always, and reject with feedback (from 2.3.1 a reject also rejects only the other pending asks of the same assistant message); the question tool |
| Built-in tools | read, write, edit, patch, glob, grep, shell, webfetch, websearch, todo, task and others, with 2.2.7's `read` offsets from the end, name suggestions and `skill://` files (the in-memory files of OpenCode Console workspace skills, also listed by the `skill` tool and in skill attachments; like 2.2.7, files a third-party plugin passes to its skill editor's `add` are dropped), `Exit code: N` after shell output, a stopped shell call keeping its output (2.3.0: the command gets SIGTERM, then SIGKILL after 3 s, stays listed with its file, and the call fails with the output so far, the file and the shell ID), and webfetch refusing credentials in URLs. From 2.3.0: output over the limits is cut once at the line or byte limit, so an over-long last line shows its start (`(last line cut)`), and the preview is kept when the full output can't be saved (`full output could not be saved: …`); a backgrounded shell command reports its `PID:` (also in `shell.created`, as 2.3.0's process daemon announces it), its result carries `pid` and the structured output (2.4.1 order `{shellID, exitCode, signal, killed, outputPath, pid, wallTimeSeconds, output}`, seen by plugin hooks), and its completion notice is admitted outside the location; `edit` and `write` return their summary as a string, `skill` returns `{directory, content}` and `patch` an empty object; a patch move that only changes a file's case renames it. The extension host API core does not use (constructible globals, functions passed back, per-run extensions) is in the runtime too. 2.2.7's catalog deltas, `import`/`require` of built-in modules and `fetch` redirect checks are in. ## Works, with a small difference

| Area | Difference |
|---|---|
| Plugins and AI SDK packages | Upstream runs them inside its Bun-based binary. ocd runs them in a Bun helper process and downloads Bun 1.4.4 the first time one is used (or set `OCD_BUN_PATH`) |
| Built-in AI SDK packages | Upstream bundles `@ai-sdk/cohere`, `@ai-sdk/perplexity`, `@ai-sdk/vercel` and `gitlab-ai-provider`. ocd installs them from npm on first use, at the same versions; if an install fails, the error wording differs |
| `session.http.response` plugin hook | Receives the whole response body as text instead of a stream |
| Plugin worktree strategies | Used only after the project's location has loaded; before that, worktree tools fall back to git |
| Persistent terminals and the process daemon | The same `opencode-pty` helper (0.6.0), downloaded once (sha512 and sha256 pinned per platform) instead of carried inside the binary: on the first terminal, or by the managed service at boot. `OPENCODE_PTY_BIN` overrides it like upstream |
| Mini mode (`ocd mini`) | A port of upstream's mini frontend. In 63 screens compared side by side the text was identical, except one startup race; code blocks are highlighted with syntect instead of tree-sitter, so some TypeScript and JavaScript token colours differ |
| Error texts | A few come from Rust instead of Bun or Node: file-system errors, MCP JSON-schema validation and network errors |
| Client certificate keys | Bun's BoringSSL also presents P-521 ECDSA keys and reads PKCS#8 keys encrypted with PKCS#12's RC2 and RC4 schemes. ocd's TLS stack (rustls with ring) can't sign with P-521, and those legacy schemes aren't read: such a certificate fails every request with `FailedToOpenSocket`, where upstream presents it |
| Start-up events | A new session's start-up notifications arrive about 0.5 s sooner; same events, same order |
| Stopping `ocd run` | On SIGINT/SIGTERM ocd interrupts a background job's session once its input is delivered, with `resume: true` (upstream interrupts when the session starts), so a cancelled job's notice can't hold up the exit. Same output and exit codes |
| Tool failure events | When several tool calls in one response fail instantly (unknown tool, unparseable input), upstream records some of the failures in the middle of the response, where its runtime's scheduler happens to yield; ocd records them after it |
| Automations (2.3.1, on by default since 2.4.1) | On unless the top-level `automations: false` turns them off for a directory (`experimental.automations` and `experimental.schedules` are dropped with a "removed" warning): timers (`at`, `every`, `cron` in a zone, `expires`), prompt actions to a session or to a new subagent child per run, model-free Code Mode actions with state and one send, and (2.4.1) shell actions (`{type: "shell", command}`: the fixed command approved once at creation with the shell tool's requests, never saved as a pattern; each run starts it without a model or timeout, advances on launch and records `Exit code: N` and its output when it exits; a missing directory or creating session pauses it). Code actions get `fetch` (2.4.1), authorized at creation like their tools (`webfetch`; referencing `Bun` asks for `read`, `edit` and `external_directory` even though ocd has no Bun globals), no 20-call cap, and may call `shell`, renames and worktrees (only the automation tools and `opencode.session.move` are refused). The tools are `create`, `list`, `pause`, `resume` and `delete` in the `automation` namespace (`tools.automation.create`, direct `automation_create`), `/automation` uses 2.4.1's text, and the six routes, list, get, pause, resume and delete answer `403` (and the tools fail) where automations are off, while automations whose folder is gone stay manageable. Plugins call `ctx.experimental.automation.create/list/delete` through the same handlers (asks settled unattended). Pause/resume, the KV lease `automation:leader` and the rewake after a restart work on the same `automation` table, so ocd and upstream list and run each other's automations. Event triggers are in their own row. Plugin activation is part of building a location in ocd, so it does not count toward a code action's 30 s cap |
| Automation event triggers (2.4.1) | `{type: "event"}` triggers watch a connected server's push event: created from a tool call in a local session after the `opencode_watch_mcp_event` permission and the server's push type and argument checks, opened by the lease holder (an event-only database keeps the lease) and followed through the Location's MCP `follow`, which waits for a disconnected server and reopens a broken stream from the last committed cursor indefinitely; rechecked (creating session and agent, permission) before each stream and run, run with the event quoted as untrusted data (a prompt) or as `input.event` (code), with `event_position` (`{agent, cursor}`) committed per event and resumed from after a reconnect, a pause or a restart. A rejected or terminated stream, a removed or disabled server and a revoked permission pause it; `expires` ends it between deliveries; an event prompt over 32 KiB is skipped (`last_outcome: "skipped"`) and the watch moves past it. Where automations are off a watch is held like a timer: it stays active with `last_outcome: "disabled"`, is checked again an hour later and starts from now when it reopens (its cursor cleared); an open one closes on its next update or the next reconcile. Watches a 2.3.1 process created in the same database run here too, and the other way round |
| `pair --remote` | A native OpenTunnel client (`crates/oc-tunnel`) replaces upstream's JavaScript SDK. It keeps the tunnel in the same place, so ocd, upstream and the opentunnel CLI share a device's tunnel. Tested against a local stand-in for the service, not yet against opentunnel.xyz |
| Image previews in the TUI | `session.image_preview` (user and tool-result images in the transcript, mini mode's scrollback) and `prompt.image_preview` (attached images above the prompt, mini mode's footer), both off by default, the preview dialog (click an image, `prompt.images.view` / `<leader>i`, `←`/`→`): the Kitty graphics protocol, Sixel or quadrant characters, chosen and encoded like OpenTUI 0.8.4 (XTVERSION, the Kitty query, DA1 attribute 4, `CSI 14 t`, tmux, `OPENTUI_IMAGE_PROTOCOL`, `OPENTUI_GRAPHICS`). Kitty images always go out whole on the raw transport: OpenTUI's per-frame upload budget, its file and zlib transports and its retry of oversized uploads are left out. Rescaled pixels (Sixel, Kitty copies at 4x the shown size) come from ocd's own area filter, which can differ from stb_image_resize2 by a rounding step; PNG ICC profiles are not applied; after a resize the window's pixel size is read from the pty instead of asked again. The diff viewer's image preview is not ported |

## Different on purpose

| Area | Difference |
|---|---|
| Name | The program name, help text and logo say `ocd` / `opencode-d`. Config, data folders, `OPENCODE_*` variables, the HTTP API and plugin package names keep opencode's names |
| TUI working status line | After you press Enter, a line above the prompt shows what's happening: waiting for the model, thinking, writing, running a tool, retrying or compacting. It also shows a timer ticking every second, the output token count and the interrupt key. A running shell command goes on the row below. Upstream shows only its moving progress bar, which ocd keeps, plus a live "Thinking" row in the transcript, which ocd leaves out while the status line shows it |
| Home and End in the prompt | With text in the prompt, Home and End move to the start and end of the current line, in the full TUI and in mini mode. With an empty prompt they keep upstream's bindings: in a session, the first and last message (`session.first`/`session.last`). Upstream moves to the whole prompt's start and end on the home screen and scrolls the session either way |
| `ocd upgrade` and update checks | Installs from ocd's GitHub releases with checksum verification, and checks once a day instead of every 10 minutes ([details](INSTALL.md#upgrading)) |
| Heap snapshots | The server has no JavaScript heap, so `POST /api/debug/heap-dump` answers `500 UnknownError`. `ocd debug heap-dump --server URL` still captures one from an upstream server |
| Version | `ocd --version` shows ocd's own build next to the compatible opencode version. Clients, plugins and the service see 2.4.1 on the `latest` channel ([details](INSTALL.md#versions)) |
